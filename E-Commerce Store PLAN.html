01

Project Overview

An automated research tool that accepts an online store name or URL, identifies the correct website, crawls public pages, detects e-commerce and marketing technologies, and produces a structured store profile ready for sales outreach.

Core objective: One store URL → verified public-page research → evidence-backed store profile → explainable fit score and marketing-gap note → JSON / Excel / PDF report. Target a usable MVP in 3 weeks, then extend only after validation.

The problem: manual research currently takes 20–40 minutes per store, produces inconsistent records, and limits the number of stores that can be assessed. This tool eliminates that bottleneck entirely.

3-Week Implementation Plan — Revised

Delivery principle: Build a narrow, reliable MVP first. Do not attempt every field, every platform and perfect automation in the first week. The three weeks are a target, not a guarantee; confirm scope and available development time with the company.
Week 1
Foundation + reliable scrape-to-JSON pipeline
  • Confirm required fields, sample stores, allowed sources, output schema and acceptance criteria with the company.
  • Create FastAPI project, GitHub repository, environment configuration, logging and basic tests.
  • Implement URL validation, reachability checks, redirect handling and safe store URL verification.
  • Build a bounded Playwright crawler and extraction for homepage, selected product pages and social/contact links.
  • Prefer JSON-LD / schema.org, then platform-aware selectors, then HTML fallbacks; store source URL and timestamp for each finding.
  • Week 1 exit test: one approved store URL produces a validated JSON record; failures return clear statuses, not crashes.
Week 2
Technology detection + validation + scoring + reports
  • Add deterministic platform and marketing-technology fingerprints with evidence and confidence levels.
  • Add bounded popup / email / SMS form checks; record which pages were checked and what was observable.
  • Implement field normalisation, deduplication, explicit statuses and persistence (SQLite for the MVP).
  • Agree fit-score criteria and weights with the company; implement an explainable score and score breakdown.
  • Add Groq only for a concise gap narrative based on validated evidence; validate its output and provide a no-AI fallback.
  • Generate JSON, Excel and PDF from one canonical profile; add a simple frontend for input, progress, results and downloads.
  • Week 2 exit test: a small test set completes end-to-end and the same source data appears consistently in all exports.
Week 3
Quality assurance + deployment + handoff
  • Build a representative test set: accessible stores, redirects, non-store domains, slow sites, missing fields and blocked sites.
  • Manually verify a sample (target 15–20 stores) and report field-level verified / incorrect / unavailable counts.
  • Fix high-impact issues; measure crawl duration, memory use, failure rate and AI quota usage.
  • Deploy only after checking Playwright browser dependencies, memory limits, timeouts, concurrency and persistent-storage requirements.
  • Prepare README, setup instructions, environment-variable list, user guide, known limitations and company handoff.
  • Week 3 exit test: company can run a test, understand evidence and statuses, export reports and reproduce the setup.
Scope control: 50-store testing is a stretch target, not a core acceptance condition. First prove quality on a smaller, representative sample. Add bulk processing only after single-store reliability, rate limiting and resource usage are measured.

Data Quality, Limitations & Responsible Use

  • Use only publicly accessible information and respect robots.txt, access restrictions and applicable law.
  • Use a responsible crawl pace; skip sites that actively block automation as required by the brief.
  • A detected script or integration is evidence a technology may be present — it does not prove the store uses every feature.
  • Dynamic content, geolocation, consent banners, login requirements and anti-bot protections affect what is visible to the scraper.
  • Follower counts and named contacts may not be publicly accessible; mark these fields Unavailable rather than guessing.
  • Never invent missing values. Use explicit statuses: Found · Not found · Unavailable · Unverified · Blocked.
  • Keep a record of the source page and timestamp for key findings so the team can verify results.
  • The fit-score formula must be documented and approved by the team before the final report — the brief does not prescribe weights.
  • AI provider quotas and model names change. Check current provider documentation; implement retries with backoff, caching and a graceful fallback.
  • Protect against SSRF: block localhost, private / link-local IP ranges and non-HTTP schemes; validate DNS and redirect destinations.
  • Set per-page and per-store timeouts, maximum pages, response-size limits and low concurrency. Always close browser contexts.
  • Minimise personal data collection; define retention, access control, deletion and log-redaction rules with the company.
  • Do not promise a fixed runtime or zero operating cost until measured on the chosen host and representative stores.
  • Persist crawl history and cache results to avoid repeatedly visiting the same store; provide a manual refresh option and show when data was last checked.

Engineering Notes, Advice & Things to Take Care Of

Most important recommendation: Treat this as an evidence-collection and lead-research system, not simply a web scraper with an AI prompt. Reliability, traceability and honest handling of missing data matter more than the number of fields the first version claims to collect.

A. Build in this order

  1. Input safety and URL verification: accept only HTTP / HTTPS, normalise domains, handle redirects and reject private or local network destinations.
  2. One-store vertical slice: crawl a small page set and produce a stable JSON record before adding AI, scoring or a polished dashboard.
  3. Evidence-backed extraction: every important field should retain its source URL, extraction time, status and (where practical) a short evidence snippet.
  4. Deterministic rules: use code for extraction, technology fingerprints, normalisation and scoring. AI should explain evidence, not determine facts.
  5. Exports and UI: build these from one canonical validated profile so JSON, Excel and PDF never disagree.
  6. Bulk processing last: add queues / batches only after a single-store run is reliable and resource limits are measured.

B. Data quality rules

  • Use a consistent field structure: value, status, source_url, checked_at and optional confidence.
  • Keep Not found separate from Unavailable, Blocked and Not checked. A missing observation is not proof that a feature does not exist.
  • For technology detection, store the matched fingerprint (script URL, DOM marker or asset path) and confidence. Avoid binary claims from one weak signal.
  • For product prices, preserve displayed value and currency. Do not compare prices across currencies without conversion rules and a recorded exchange-rate source.
  • Deduplicate products by canonical product URL or stable platform ID; normalise tracking URLs carefully.
  • Keep raw evidence separate from AI-generated commentary. Label generated text as interpretation, not verified fact.

C. Fit-score design

  • Get the company to approve criteria and weights before coding the final score. Any sample weights are proposals, not business truth.
  • Make the score explainable: show each factor, its contribution, the evidence used and the reason a factor was excluded.
  • Do not treat inaccessible or blocked data as zero. Use an explicit unknown state and calculate coverage / confidence separately.
  • Test the score against examples the company considers good-fit and poor-fit stores; adjust only with documented approval.
  • Keep scoring deterministic and version the formula so historical scores remain interpretable after rule changes.

D. Browser, performance and reliability

  • Reuse a browser process where appropriate, but isolate each crawl in its own context and always close pages, contexts and browser processes in cleanup blocks.
  • Use navigation and selector timeouts; avoid long fixed sleeps where a specific element can be checked safely.
  • Limit pages per store, response size, concurrency and total crawl duration. Add retries only for transient failures, with backoff.
  • Do not repeatedly retry 403 / 429 / CAPTCHA / access-denied responses. Stop or mark the site Blocked.
  • Test Playwright on the actual deployment host early. Browser binaries, system dependencies and memory can make a free web tier unsuitable.
  • Measure runtime, success rate, memory, CPU and cost. Do not claim a fixed per-store time until benchmarked.

E. Security and privacy checklist

  • Protect against SSRF: reject localhost, private, link-local and reserved IP ranges; validate DNS results and every redirect destination.
  • Never execute downloaded scripts or treat scraped page text as trusted instructions. Treat website content as untrusted input.
  • Keep API keys in environment variables / deployment secrets; commit only a .env.example, never the real .env.
  • Restrict CORS to the deployed frontend, validate request sizes and input types, and add basic API rate limiting.
  • Minimise personal data collection; agree retention and deletion rules. Avoid collecting personal contact names unless explicitly required and approved.
  • Do not bypass logins, paywalls, CAPTCHAs, access controls or anti-bot measures. Respect site terms, applicable law and the company's approved crawl policy.

F. Testing checklist before handoff

  • Test valid store URL, ambiguous store-name matches, non-store website, invalid URL and unreachable domain.
  • Test redirects, slow pages, JavaScript-heavy pages, empty product catalogues, currency variants and duplicate products.
  • Test missing email / social links, cookie banners, popup timing, blocked pages and partial crawl failures.
  • Test Groq unavailable, quota exceeded, malformed AI output and slow AI response; scraper and exports should still work.
  • Test Excel / PDF output for empty values, long text, special characters, multiple stores and large result sets.
  • Verify every score and factual statement in the report can be traced to stored evidence or a labelled interpretation.

G. Practical project-management advice

  • Maintain a task board with owner, status, blocker and acceptance test for each module. Agree interfaces before parallel development.
  • Use feature branches and pull requests; require a basic test before merging to the main branch.
  • Freeze the JSON schema and scoring rules early. Changes after frontend and export work begins create avoidable rework.
  • Keep a known-sites test fixture set so every scraper change can be checked against previously verified results.
  • Reserve the final 2–3 days for bug fixes, deployment and handoff—not new features.
  • Document what the tool cannot reliably detect. A transparent limitation is better than a misleading result.
Do not overbuild the first version: defer login, user roles, sophisticated dashboards, continuous monitoring, social follower-count collection, large-scale parallel crawling and advanced AI agents unless the company explicitly requires them. Prioritise a dependable single-store workflow and an auditable report.
