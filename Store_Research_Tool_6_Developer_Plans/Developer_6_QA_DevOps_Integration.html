2. Requirements before starting

Skills / knowledge

Git/GitHub, branch protection, GitHub Actions, pytest, Docker, environment configuration, logs, deployment troubleshooting, test planning and issue triage.

Environment / access

GitHub repository access; approved CI secrets; Docker; pinned Python/browser versions; agreed test-store fixtures; staging environment credentials stored as secrets. Never commit API keys, cookies or personal data.

Dependencies on other developers

All developers submit small reviewed PRs against the agreed branch strategy. D6 merges only after checks and owner approval. D6 does not mark a feature accepted without its owner’s test evidence and the shared gate criteria.

Non-negotiable: Do not build against a guessed interface. If an input schema, endpoint or output is not ready, raise the blocker and work on a listed independent task. Never rename shared fields locally to make your module pass.

3. Shared system workflow — same for all six developers

1 · User inputD5 collects a store name or URL and sends the agreed request to D1. D1 validates and canonicalises the target before any navigation.
2 · Safe crawlD1 creates the job and calls D2. D2 performs a bounded public-page crawl and returns a typed CrawlBundle with page URLs, page types, status, scripts, timestamps and dynamic observations.
3 · Deterministic extractionD3 consumes CrawlBundle and emits field-level EvidenceRecords. Values are not filled by guesswork; every found fact carries source/method/status metadata.
4 · Validation and analysisD4 validates evidence, calculates the deterministic explainable score and optionally asks Groq to produce a short evidence-grounded narrative. AI failure falls back to a template.
5 · Persist and presentD1 persists the result and exposes job/profile/export APIs. D5 renders the exact API response, including unknown/blocked states, score coverage and source evidence.
6 · Verify and releaseD6 runs CI, fixture/integration/E2E tests, controls merge/release gates and verifies the deployed system. Module owners fix defects in their own modules.

5. Shared weekly milestones and gates

End of Week 1 · Contract gate

One agreed API/profile/evidence schema; safe URL boundary; Playwright CrawlBundle; fixture-first deterministic extraction; health endpoint; CI; hosting feasibility proved. Three reference archetypes represented by fixtures: Shopify, WooCommerce and Magento.

End of Week 2 · Integrated core gate

A local end-to-end workflow can return a schema-valid profile for the reference set. Marketing/review technology indicators, forms/offers, statuses, deterministic score, optional AI narrative/fallback and dashboard are connected. Single-store flow remains the priority.

End of Week 3 · Feature freeze

All must-have features are integrated: research, evidence/status, score breakdown, narrative/fallback, profile UI and JSON/Excel/PDF exports. Batch mode is enabled only if it has passed isolation tests; otherwise it stays deferred.

End of Week 4 · Release gate

20-store field-level benchmark completed or exceptions documented; regression/security/performance checks passed; frontend and backend deployed; README, user guide, known limitations and rollback notes handed over. A 50-store run is a stretch/load exercise, not a substitute for verified quality.

6. Coordination rules — prevent downstream rushing

  1. Contract review happens early in Week 1. D1, D2, D3 and D4 agree the data boundaries; D5 confirms display requirements; D6 records the version and sample payload. Changes after freeze require affected-owner approval.
  2. The sequence is strict: D1 URL guard → D2 CrawlBundle → D3 EvidenceRecords → D4 validation/score/narrative → D1 persistence/API → D5 UI/reports. Parallel work is allowed only against signed interfaces or mocks.
  3. No developer marks a handoff “ready” without a sample output, tests and failure-state behaviour. The receiving developer confirms acceptance before dependent work is treated as unblocked.
  4. Every PR names the receiving module and any contract impact. D6 schedules merge windows; a green CI build is necessary but not sufficient if the receiving owner has not approved the interface.
  5. Daily blockers are visible to all six. If a dependency slips, the downstream developer switches to fixture tests, documentation, error handling or another independent task from this plan—not a guessed implementation.
  6. Sunday is an integration gate, not a seventh unstructured coding day. Each owner demonstrates the weekly deliverable, updates issue status and commits next-week dependencies.
  7. After Week 3 Sunday feature freeze, do not add features during Week 4 unless the team lead approves a release-critical change and its testing impact.

7. Engineering rules applying to every role

Hours and cadence

Each developer plans 3 focused hours Monday–Saturday and 4 hours Sunday: 22 hours/week, 66 development hours across Weeks 1–3, 22 release hours in Week 4, 88 total per developer. Team total: 528 person-hours.

Daily rhythm

Within the allocated hours, reserve about 10 minutes for dependency/status sync, the majority for the assigned task, and the final 15–20 minutes for tests, a PR/update and blocker handoff. Sunday includes the weekly integration gate and next-week commitment.

Branch and PR discipline

Use feature branches named `devX/short-task`; open small PRs to `develop`; require one reviewer and green checks; D6 controls merge windows. `main` is release-only. Do not force-push shared branches or edit another owner’s module without agreement.

Contract-first development

Shared schemas, API paths, status names and interface signatures are frozen at the Week 1 gate. Any change requires a short proposal, impact list, approval from affected owners and version/update to examples/tests. No private field renaming.

Definition of Done

A task is done only when code is committed, relevant tests pass, a sample output is attached, error/unknown behaviour is considered, docs are updated where needed, PR is reviewed and the receiving developer confirms the handoff.

Blocker rule

Raise blockers immediately with: what is blocked, exact interface/input, reproduction steps, owner needed and decision deadline. The dependent developer must switch to a listed independent task; never implement a guessed interface just to stay busy.

Status semantics

Use `Found`, `Not observed`, `Unavailable`, `Unverified`, `Blocked` and `Error` consistently. “Not observed” means not seen in the scanned pages/window; it does not prove that the store does not use a tool or feature.

Responsible crawling

Inspect public pages only. Respect robots/access restrictions and polite delays. Do not bypass login, CAPTCHA, paywalls, geo/access controls or consent choices. Detect consent banners; do not automatically accept/reject/dismiss them.

Security boundary

Only HTTP/HTTPS. Block loopback/private/link-local/metadata IPs; re-check DNS and every redirect; restrict ports, page count, response size, page/job time and concurrency. Never fetch arbitrary user-supplied URLs outside the URL guard.

AI boundary

Groq is optional and narrative-only. It may summarise validated evidence and explain known gaps. It must not scrape, infer country/technology, fill missing values, alter status or calculate fit score. Store page text is untrusted input.

Unknowns and scoring

Unknown/blocked/unavailable fields are not zero or negative by default. Score only approved criteria, version the weights and show coverage/insufficient-data state. Never claim universal accuracy from a small sample.

Scope control

Must-have: one-store end-to-end research, evidence/status metadata, core store/product/contact/social fields, agreed platform/marketing/review signals, explainable score, optional narrative fallback, dashboard and JSON/Excel/PDF exports. Stretch: 50-store batch, follower counts, broad platform catalogue and advanced popup/geo handling.

Testing hierarchy

Offline fixtures first; mocked pipeline second; controlled live-store tests third; manually verified benchmark fourth. Do not make CI dependent on external store uptime or live Groq quota.

Release protection

After Week 3 Sunday feature freeze, Week 4 is limited to bug fixes, verification, usability polish, documentation and deployment. New features require explicit approval and must not displace release-critical tests.
